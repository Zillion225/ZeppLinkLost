Bluetooth Lost Detection Implementation Plan

A staged plan for detecting when the watch loses its phone connection, updating the watch UI, issuing exactly one vibration alert, and determining whether reliable monitoring can continue after the app leaves the foreground.

Hello World validated on device Project: LinkLost Target display: 480 px round Current configured API target: 4.0
Key constraint: foreground connection detection is supported by the documented BLE API. Background reliability on Active Max remains a hardware validation gate and must not be assumed.

01 · Product definition

Objective and scope

The watch should detect a real transition from phone-connected to phone-disconnected and notify the wearer once. It must not vibrate continuously, and it must not produce a false alert merely because the app was opened while already disconnected.

MVP includes
  • Read the current phone/BLE connection state.
  • Display CONNECTED or DISCONNECTED.
  • Listen for connection-state changes while the app is open.
  • Vibrate once on a confirmed connected → disconnected transition.
  • Re-arm the alert after the phone reconnects.
  • Clean up listeners when the page is destroyed.
Deferred until MVP works
  • User settings and a Settings App.
  • Quiet hours and configurable vibration patterns.
  • Reconnect notifications.
  • Localization and final visual design.
  • Store submission packaging.

02 · Technical direction

Proposed detection flow

The first implementation will use connectStatus() for the initial snapshot and addListener() for subsequent changes from @zos/ble. Alert logic will be isolated from UI rendering so the same state machine can later be evaluated inside an App Service.

ReadQuery the initial connection state.
ListenSubscribe to connection changes.
EvaluateCompare current and previous states.
ConfirmOptionally debounce brief drops.
AlertUpdate UI and vibrate exactly once.
Design rule: the first status read initializes the state only. It never triggers a disconnect alert. An alert requires evidence that the previous known state was connected.

03 · Core behavior

Connection state machine

Previous state New state UI action Vibration Reason
Unknown Connected Show connected No Initial state only.
Unknown Disconnected Show disconnected No Avoid an alert immediately after app launch.
Connected Disconnected Show disconnected Once This is the target lost-phone transition.
Disconnected Disconnected No change No Prevents repeated alerts.
Disconnected Connected Show connected No for MVP Re-arms the next disconnect alert.

04 · Work breakdown

Implementation phases and decision gates

1

Baseline and API compatibility check

Preserve the working Hello World baseline, verify the installed type definitions and the generated app.json, then confirm that the Active Max runtime accepts the documented @zos/ble APIs. Record device and Zepp App versions for repeatable testing.

Gate: the existing app still previews successfully and the BLE imports build without errors.
2

Foreground connection-status proof of concept

Replace the Hello World content with a minimal status screen. Call connectStatus() during page build and render a clear green connected state or red disconnected state. Add structured device logs for each reading.

Gate: manually toggling phone Bluetooth produces the correct state after reopening the app.
3

Live transition listener

Register addListener(callback) when the page becomes active, update the UI from the callback, and call removeListener() during teardown. Confirm that repeated page entry does not create duplicate listeners or duplicate logs.

Gate: the foreground UI changes without reopening the app when Bluetooth is disabled and restored.
4

Single disconnect alert

Add the state machine and use Vibrator from @zos/sensor. Start with a standard finite notification or strong-reminder vibration. Keep vibration behind one function so the pattern can be changed later without altering connection logic.

Gate: one connected → disconnected transition causes one vibration, no matter how long disconnection lasts.
5

False-positive protection

Test short connection interruptions. If Active Max reports transient drops during ordinary use, add a short confirmation delay before alerting and cancel it if the connection returns. The first version should use a fixed internal delay; user configuration can come later.

Gate: momentary reconnects do not create misleading alerts, while a sustained loss still alerts promptly.
6

Background feasibility prototype

Add a minimal continuous App Service only after foreground behavior is proven. Configure the app-service module and device:os.bg_service permission, request user permission, and experimentally verify whether BLE state callbacks remain available when the UI is closed, the screen sleeps, and the device reboots.

Critical gate: Active Max produces a reliable alert after the Device App UI has been exited.
7

Hardening and productization

Once the background gate passes, add persistence for enablement state, safe service start/stop, permission-denied UX, power-saving behavior, settings, localization, final app naming, icons, and release validation.

Gate: the feature survives normal daily-use scenarios without duplicate alerts or unacceptable battery impact.

07 · Definition of done

MVP acceptance criteria

  • The current connection status displayed on the Active Max matches the real phone state.
  • A live connected → disconnected transition is detected without reopening the app.
  • The watch vibrates once per disconnect event.
  • Starting the app while disconnected does not vibrate.
  • Remaining disconnected does not create repeated vibration.
  • Reconnecting re-arms detection for the next disconnect.
  • Page destruction removes the BLE listener and prevents duplicate callbacks.
  • Logs clearly identify initial reads, transitions, alert decisions, and teardown.
  • The app still builds and previews through Zeus on the physical Active Max.
Product acceptance is separate: LinkLost becomes genuinely useful only if Phase 6 proves background monitoring. A successful foreground MVP does not prove background capability.

08 · Unknowns and safeguards

Risk register

Risk Level Response
BLE callbacks may not remain active in an App Service on Active Max. High Build a focused background prototype immediately after the foreground MVP; do not build settings first.
Zepp OS may restrict continuous services or allow only one at a time. High Handle permission/service-start failure visibly and test conflicts with existing services.
Short BLE interruptions may produce false alarms. Medium Measure real event timing and add a cancellable confirmation delay if needed.
Duplicate listeners may create repeated alerts. Medium Use explicit lifecycle ownership and always remove the listener during teardown.
Continuous monitoring may affect battery life. Medium Use event callbacks rather than polling, avoid timers where possible, and compare daily battery drain.
The handoff says API 4.2, while the current app.json targets 4.0. Low Keep the generated target initially; only change it when a required API or device capability justifies the change.
